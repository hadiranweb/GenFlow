# نود ارزیابی — ربات تلگرام + سرور گزارش

سرویس مستقل (Node.js + TypeScript + grammY) که «فرایند اصلی نود ارزیابی» را روی تلگرام اجرا می‌کند:

```text
/start → رضایت
   │
   ├─ ۱) ارزیابی ذهنیت MindsetGate-EP (۱۲ پرسش رنجی MG-A/B/C) ── فرمول قطعی، بدون LLM ─→ 🏷️ لیبل داخلی
   │        • برچسب است، نه فیلتر: مسیر را متوقف نمی‌کند و به کاربر نمایش داده نمی‌شود
   │        • فقط در پرونده/دیتابیس می‌ماند (سطح مدیریت)
   │
   ├─ ۲) ادامهٔ بی‌وقفه (بدون اعلام مرحله): عارضه‌یابی پنج‌لایه ۲۰ پرسش در ۵ لایه (نسخهٔ ۰ تا ۱۰ طبق پلی‌بوک)
   │        • هر پرسش دو ساید: پاسخ رنجی (وارد محاسبه) + توضیح متنی (اختیاری، فقط تفسیر)
   │        • هر پاسخ بلافاصله ذخیره می‌شود (ادامه با /resume)
   │
   ├─ ۳) ماتریس قطعی: نمرهٔ محورها، شکاف تا هدف ۷۵، عارضه‌های ≤ ۴، اولویت = شکاف × وزن
   │
   ├─ ۴) تفسیر دولایه:
   │        • داخلی و رنجی (همیشه): قاعده‌محور، بدون مدل
   │        • عمیق (کلید مدیر): مسیر انسانی + به‌صورت اختیاری پیش‌نویس AI با متن‌ها
   │
   └─ ۵) سند عارضه‌یابی HTML (تک‌فایلی) با شمارهٔ سری → ارسال در تلگرام + لینک امضاشده
```

**سه اصل غیرقابل‌مذاکره در این پیاده‌سازی:**

1. **هیچ عددی از مدل زبانی نمی‌آید.** نمرهٔ ارزیابی و ماتریس با فرمول نسخه‌دار محاسبه می‌شوند؛
   مدل فقط در «تفسیر عمیق» متن می‌نویسد.
2. **ارزیابی اولیه برچسب است، نه فیلتر.** مسیر را متوقف نمی‌کند، به کاربر نمایش داده نمی‌شود و
   در ادامهٔ فرایند اثر ندارد (ADR 0002).
3. **شکست صادقانه.** اگر مدل شکست بخورد، سند بی‌تحلیل نمی‌ماند؛ تفسیر داخلی جایگزین می‌شود و
   همین موضوع در خود سند نوشته می‌شود.

منابع طراحی:
- فرایند اصلی: `docs/diagrams/main-process.drawio.xml` + `docs/process-spec-fa.md`
- بررسی و تصمیم‌ها: `docs/main-process-review-fa.md` + `docs/adr/0002-label-not-filter.md`
- پیش‌نویس دو بانک پرسش: `docs/reference/stage1-screening.owner-draft.yaml` · `stage2-diagnostics.owner-draft.yaml`
- منبع انتخاب بانک‌ها: `docs/reference/questions.source-of-truth-v1.2.yaml` (نسخهٔ مرجع Drive)
- منبع بانک فعال ۱۲سؤالی: شیت `MindsetGate-EP (۱۵)`؛ مرجع تطبیق: `docs/reference/mindsetgate-ep-12-owner-copy.json`
- بانک SJT قدیمی/غیرفعال: `data/questions/gate.mindset.example.yaml` (۱۵ سناریو؛ در این فرم فعال نیست)

## ۱. راه‌اندازی سریع (لوکال)

```bash
cd node-eval-bot
npm install

# الف) بدون تلگرام — برای دیدن گزارش نمونه
npm run smoke              # سه سند نمونه (مطلوب/مرزی/بحرانی) در out/ می‌سازد
npm run lint:questions     # اعتبارسنجی YAML محتوا (پرسش‌ها، وزن‌ها، آستانه‌ها، کلیدهای مدیر)
npm test                   # تست‌های کامل (شامل تطبیق ۱۲ متن منبع و آزمون‌ها)

# ب) با تلگرام
cp .env.example .env       # BOT_TOKEN را از @BotFather بگیرید
npm run dev
```

بررسی بدون تلگرام:

```bash
npm run build
npm run seed                                   # یک پروندهٔ نمایشی می‌سازد و لینک می‌دهد
BOT_MODE=disabled node dist/index.js           # سرور بدون اتصال به تلگرام
curl http://localhost:8080/health
```

## ۴. مرحلهٔ ۱ — ارزیابی ذهنیت MindsetGate-EP (لیبل، نه فیلتر)

**بانک فعال: ۱۲ سؤال رنجی MG-A/B/C** از شیت `MindsetGate-EP (۱۵)` در فایل «آرشیو — بانک سوالات v0».
سه سناریوی SJT همان شیت فعلاً انتخاب نشده‌اند. متن دقیق ۱۲ سؤال و شناسه‌های منبع در
`docs/reference/mindsetgate-ep-12-owner-copy.json` ثبت و با آزمون خودکار تطبیق داده می‌شود.
نسخهٔ بانک: `gate-mindset-ep-1.0.0`؛ سه سؤال معکوس: `MG-A3`، `MG-B3` و `MG-C3`.

| محور | کد منبع | سؤال‌ها | معکوس |
|---|---|---:|---|
| منبع کنترل | MG-A | ۴ | MG-A3 |
| فاعلیت و خودتنظیمی | MG-B | ۴ | MG-B3 |
| تفکر مسئله‌محور | MG-C | ۴ | MG-C3 |

نمره‌گذاری از پاسخ‌های تعدیل‌شدهٔ ۰..۱۰ با وزن برابر سه محور انجام می‌شود؛ پاسخ معکوس
با `۱۰ − پاسخ خام` تعدیل می‌شود. لیبل فقط در پروندهٔ داخلی ذخیره می‌شود: مسیر را متوقف
نمی‌کند، به کاربر نشان داده نمی‌شود و در انتخاب یا تفسیر سؤال‌های بعدی دخالتی ندارد.

> `gate.mindset.example.yaml` بانک جداگانهٔ ۱۵ سناریوی SJT است و در حال حاضر فعال نیست.
> آن را با شیت `MindsetGate-EP (۱۵)` اشتباه نگیرید: شیت موردنظر ۱۲ خودگزارشی + ۳ سناریوی
> SJT دارد، ولی در build فعلی فقط ۱۲ خودگزارشی وارد ارزیابی می‌شود.

## ۶. مرحلهٔ ۲ — عارضه‌یابی تفصیلی (دو ساید)

۲۰ پرسش در ۵ لایهٔ سیستم‌سازی (۴ پرسش در هر لایه، ۱ پرسش کلیدی در هر لایه) — متن و
لنگرهای ۰/۵/۱۰ مطابق فهرست نهایی ارائه‌شده توسط کاربر است (مرجع آزمون: `docs/reference/diagnostic-questions-owner-copy.json`).
مبنای فرم سند «عارضه‌یابی پنج‌لایه» و پلی‌بوک ۰ تا ۱۰ است (`0.1-draft`،
`draft_pilot_required`؛ شرح منبع در `docs/reference/five-layer-source.md`). لنگرهای
۰/۵/۱۰ زیر هر سؤال در پیام ربات نمایش داده می‌شوند و ۵ پرسش معکوس‌اند
(`L1-Q2`، `L2-Q3`، `L3-Q2`، `L4-Q3`، `L5-Q3` → `polarity: reverse`، نمرهٔ مؤثر = ۱۰ − پاسخ).
پرسش `L5-Q4` دربارهٔ اقتصاد واحد نیز در فهرست نهایی کاربر حفظ شده است. عنوان نمایشی
لایهٔ اول «بنیان و رهبری» است و نسخهٔ پرسش‌نامه `matrix-five-layer-1.3.0` است.

| لایه | وزن | پرسش کلیدی | ارجاع سند |
|---|---|---|---|
| بنیان و رهبری (Governance) | ۱.۰۰ | l1q1 — واگذاری بدون مالک | L1-Q1 |
| معماری و طراحی (Architecture) | ۱.۰۰ | l2q2 — پوشش SOP | L2-Q2 |
| جاری‌سازی (Implementation) | ۱.۰۰ | l3q1 — آزمون غیبت ۴ هفته‌ای | L3-Q1 |
| نگهداشت و پایش (Maintenance) | ۱.۰۰ | l4q1 — داشبورد KPI | L4-Q1 |
| توسعه و مقیاس‌پذیری (Scaling) | ۱.۰۰ | l5q1 — سه‌برابرشدن حجم کار | L5-Q1 |

**نظام امتیازدهی سند:** نمرهٔ هر لایه = مجموع ۴ نمرهٔ تعدیل‌شده ÷ ۲ (بازهٔ ۰ تا ۲۰، فیلد
`score0to20`؛ معادل میانگین×۲۰)، نمرهٔ کل = مجموع ۵ لایه (۰ تا ۱۰۰) و کم‌امتیازترین لایه
«گلوگاه بحرانی» است (در تساوی، لایهٔ بالادستی‌تر). نوارهای موقت سند هم در خروجی می‌آید:
لایه‌ها «ضعف (<۱۰) / در حال رشد (۱۰ تا <۱۵) / قوی (۱۵–۲۰)» از ۲۰ و رتبهٔ بلوغ کل
«نوپا (<۴۰) / در حال شکل‌گیری (۴۰ تا <۶۰) / در حال بلوغ (۶۰ تا <۸۰) / بالغ (۸۰–۱۰۰)» — مرزها پیوسته و نیم‌بازند تا نیم‌امتیازها (گام ۰٫۵) بدون طبقه نمانند — در خلاصهٔ سند و تفسیر داخلی نمایش داده می‌شود.

**ماتریس تفسیر** (`data/vocab/interpretation-matrix.yaml`): برای هر لایه «وضع موجود (As-Is)،
وضع مطلوب (To-Be)، راهکارها و درخت کلیدواژه (۱۵ اقدام والد)» از بخش «گزارش ماتریسی شکاف»
سند استخراج شده است. مفسر داخلی از همین زبان استفاده می‌کند، مفسر عمیق AI آن را در پرامپت
می‌گیرد، سند HTML جدول شکاف را از آن می‌سازد، و ۵ الگوی بین‌لایه‌ای (مثل «معماری قوی +
جاری‌سازی ضعیف = فرایندها نوشته شده اما اجرا نمی‌شوند») به‌صورت قطعی تشخیص داده می‌شوند.

> نسخهٔ قبلی ۹محوری در `docs/reference/matrix-9axis-v1.yaml` بایگانی شده است.
> بخش عمومی فرم سند (اطلاعات پایه و نبض کسب‌وکار) در ماتریس تفسیر ثبت شده اما هنوز در
> جریان ربات نیست (نیازمند ورودی انتخابی/متنی آزاد — فاز بعد).

**محاسبه (قطعی، بدون مدل):**

```
answerRate_d  = پاسخ‌داده / کل
score_d       = میانگین پاسخ‌های نرمال‌شدهٔ محور × ۱۰۰
overall       = Σ(وزن × score_d) / Σ وزن محورهای پاسخ‌داده
gap_d         = max(0, ۷۵ − score_d)          ← امتیاز مطلوب: target_index = ۷۵
priority_d    = gap_d × وزن_d                  ← ترتیب اقدام‌ها
symptom       = هر گزاره با نمرهٔ ≤ ۴ («عارضهٔ مشاهده‌شده»؛ symptom_threshold = ۴)
band          = ۷۵+ مطلوب · ۶۰..۷۵ مرزی · ۴۰..۶۰ نیازمند اصلاح · <۴۰ بحرانی
```

**دو ساید بودن:** توضیح متنی کاربر **در محاسبه وارد نمی‌شود**؛ فقط در پرونده، سند و
(در صورت فعال بودن «تفسیر عمیق AI») در بستهٔ ارسالی به مدل می‌آید. ناسازگاری بین عدد و
توضیح، به‌عنوان «نیازمند روشن‌سازی» در سند برجسته می‌شود.

**کلیدهای مدیر** (فعلاً در جدول `settings` دیتابیس؛ داشبورد در فاز بعد):

| کلید | اثر |
|---|---|
| `deep_interpretation` | روشن → مسیر تفسیر عمیق (انسانی و/یا AI) اجرا می‌شود؛ سند «پیش‌نویس» علامت می‌خورد |
| `ai_interpretation` | فقط با روشن بودن کلید بالا معنا دارد؛ متن‌های آزاد کاربر به مدل می‌رود |

تغییر مقدارها:

```bash
sqlite3 data/app.db "UPDATE settings SET value='true' WHERE key='deep_interpretation';"
sqlite3 data/app.db "UPDATE settings SET value='true' WHERE key='ai_interpretation';"
```

**نمونهٔ SJT قدیمی:** `data/questions/gate.mindset.example.yaml` (۱۵ سناریو) و موتور آن برای
آزمون/آرشیو حفظ شده‌اند، اما بانک فعال نیستند. بانک فعال فعلی فقط ۱۲ سؤال رنجی MG-A/B/C است.
سه سناریوی SJT شیت MindsetGate-EP نیز فعلاً انتخاب نشده‌اند.

## ۷. اتصال مدل زبانی (فقط تفسیر)

```env
LLM_PROVIDER=openai
LLM_BASE_URL=https://api.openai.com/v1      # یا OpenRouter / Ollama: http://localhost:11434/v1
LLM_API_KEY=sk-...
LLM_MODEL=gpt-4o-mini
```

- مدل **نباید عدد جدید** بسازد؛ `zone`/`verdict` محاسبه‌شدهٔ ما در نهایت غالب است.
- خروجی صرفاً JSON؛ اگر نامعتبر بود → **مفسر قطعی** جایگزین می‌شود و در خودِ گزارش نوشته می‌شود
  که «تفسیر با مدل زبانی انجام نشد».
- بستهٔ ارسالی فقط سؤال‌های سیگنال‌دار هر دامنه را می‌فرستد (کاهش توکن و گمراهی).

## ۸. سند HTML

بخش‌ها: `خلاصهٔ مدیریتی` → `تصویر وضع موجود (۵ لایه، هر لایه از ۲۰) + جدول گزارش ماتریسی شکاف` → `اولویت‌بندی بر شکاف × وزن` →
`عارضه‌های مشاهده‌شده` → `تحلیل تفصیلی` → `گلوگاه‌ها و ریسک‌ها` → `نقاط قوت` →
`ناسازگاری عدد و توضیح` → `اقدام‌های پیشنهادی` → `نیازمند گفت‌وگو` → `محدودیت‌ها` →
`پیوست ۱: تنظیمات محاسبه` → `پیوست ۲: پاسخ‌های خام و توضیحات` → `شمارهٔ سری + اثر انگشت محتوا`

- **لیبل ارزیابی مرحلهٔ ۱ در سند نیست** (تست خودکار این را تضمین می‌کند).
- تک‌فایلی، RTL، بدون CDN/فونت آنلاین (آفلاین و آرشیوپذیر)، آمادهٔ چاپ.
- همهٔ متن‌های کاربر و مدل از `escapeHtml` عبور می‌کنند.
- دانلود: فایل در تلگرام + `GET /reports/:id?t=<token>` با امضای HMAC.

## ۹. دیپلوی روی سرور

```bash
git clone <repo> && cd node-eval-bot
cp .env.example .env      # BOT_TOKEN، REPORT_LINK_SECRET، ADMIN_CHAT_ID
docker compose up -d --build
docker compose logs -f
```

`restart: unless-stopped` + `HEALTHCHECK` روی `/health` → پس از کرش یا ری‌استارت سرور خودش برمی‌گردد.
داده در `./data` می‌ماند (SQLite + گزارش‌ها) و پشتیبان‌گیری‌اش ساده است.

## ۱۰. عملیات، حریم خصوصی و عدالت

| موضوع | وضعیت |
|---|---|
| لاگ‌ها | محتوای پاسخ‌های کاربر هرگز لاگ نمی‌شود (فقط شناسه/کد سؤال/شمارنده) |
| حذف داده | `/delete` → پرونده‌ها، گزارش‌ها و رویدادها پاک می‌شوند |
| ارسال به LLM | فقط در مرحلهٔ تفسیر و به‌صورت خلاصهٔ نمره‌ها (نه متن گفت‌وگو، نه سناریوها) |
| برچسب ارزیابی | به کاربر نمایش داده نمی‌شود؛ در سند نمی‌آید؛ در ادامهٔ فرایند اثر ندارد؛ صرفاً در پرونده/سطح مدیریت |
| توضیحات متنی | اختیاری؛ در محاسبه وارد نمی‌شوند؛ فقط در مسیر «تفسیر عمیق AI» به مدل ارسال می‌شوند و این در رضایت‌نامه صریح آمده است |
| آرشیو | هر فرم/ماتریس/تفسیر/سند با **شمارهٔ سری** و شمارهٔ نشست ذخیره می‌شود (فقط-افزودنی) |
| سلامت سرویس | `GET /health` (DB، provider مدل، اندازهٔ صف گزارش) |
| تلاش مجدد گزارش | `/report` → اگر ساخت ناموفق بوده دوباره صف می‌شود (هر جلسه یک گزارش، idempotent) |
| محدودیت نرخ | پیش‌فرض ۴۰ پیام در دقیقه هر کاربر |

**ریسک‌هایی که باید آگاهانه مدیریت شوند** (تفصیل در ADR): خودگزارشی بودن SJT، نبود سنجهٔ واقعی
Action/Complain، و تصمیم خودکار در مرحلهٔ ورود. پیشنهاد پیاده‌شده: `GATE_RED_POLICY=stop` +
ثبت پرونده برای بازبینی + مسیر اعتراض + ثبت نسخهٔ سیاست در گزارش.

## ۱۲. وضعیت

**آماده:** ارزیابی ذهنیت ۱۲سؤالی MG-A/B/C با لیبل داخلی و بدون فیلتر، سپس عارضه‌یابی پنج‌لایه (۲۰ پرسش). پس از تغییر بانک، نشست‌های نیمه‌تمامی که با نسخهٔ ۱۵سؤالی قبلی آغاز شده‌اند باید تکمیل/از نو آغاز شوند؛ پاسخ‌های قبلی قابل نگاشت به MG-A/B/C نیستند.
عارضه‌یابی، دو ساید بودن (توضیح اختیاری)، ماتریس با شکاف/عارضه/اولویت، تفسیر داخلی و
عمیق، آرشیو سریال‌دار، سند HTML، صف گزارش، سرور، دیپلوی، **۹۰ تست**.

**در انتظار (فازهای بعدی، مطابق `docs/main-process-review-fa.md`):**
1. صف و فرم «تفسیر انسانی» در کنار پیش‌نویس AI (فاز ۲).
2. MCP مفسر: دستورالعمل + فرم تفسیر + کتابخانهٔ دانش (فاز ۳).
3. داشبورد مدیر: رتبه‌ها/برچسب‌ها، صف تفسیر، کلیدها، خروجی CSV (فاز ۳).
4. بازتولید سند پس از بازبینی انسانی (بدون تفسیر مجدد).
